# Integrating with CodeIgniter and migrating WordPress

The demo runs independently. A production transition requires approval, a database backup, a WordPress export and a read-only media inventory.

1. **Inventory.** Export WordPress WXR or REST data in staging, including IDs, authors, categories, tags, publication dates, featured images, attachment paths, slugs, status and full old permalinks. Record a checksum and row counts for repeatable imports. Snapshot the production database and uploads first.
2. **Map and transform.** Build a staging crosswalk of WordPress IDs to stable new IDs. Preserve slugs where possible. Resolve collisions deterministically with the old ID and record every changed URL. Map published to published and private, scheduled, pending and draft content to draft. Choose a primary category and preserve remaining labels as tags. Use a one-off trusted importer for historical timestamps. Public CRUD intentionally assigns server timestamps.
3. **Content and media.** The challenge editor uses plain text. Inspect Gutenberg blocks and shortcodes before import; convert supported text blocks and route embeds, galleries, inline images and complex layouts for editorial review or a future sanitized block renderer. Copy licensed attachments to managed storage, preserve original-to-new URL mappings and alt text in the migration inventory, and validate every cover URL. Retain the original archives until signed off.
4. **Shadow integration.** Fetch the published-only API server-side from CodeIgniter, for example GET /api/posts?limit=3 for the homepage. Set request timeouts; production can briefly cache the last good response and show an archive link during outages. Render escaped titles/excerpts and encode slugs. Proxy /blog and /api/posts to the journal under the same public domain. Keep /admin and editorial cookies on the trusted journal origin. No editor secret belongs in CodeIgniter frontend JavaScript.
5. **Verify.** Compare source and destination status counts, timestamps, a sampling of rendered articles, media availability, pagination and search. Probe old URLs and draft guesses anonymously. Test mobile navigation and editor writes on staging. Resolve or document every transformation exception.
6. **Cut over and roll back.** Freeze WordPress writes briefly, import the final delta by stable source ID, snapshot D1 and verify checksums. Install explicit one-hop 301 mappings from each historical permalink to its published destination. Preserve useful query parameters, canonical URLs and sitemap entries; draft destinations should stay private. Switch routes, watch 404s and editorial errors. Keep WordPress read-only until the rollback window closes. Revert routing and reconcile any post-cutover edits if a rollback is necessary.
